# Klubbnettside

Interactive prototype of a website platform for Norwegian sports clubs, shown with the fictional multi-sport club **Oslo Sportsklubb** (fotball, sykkel, langrenn).

```bash
npm install
npm run dev
```

Opens on http://localhost:3100.

## Demo in five minutes

0. **Klubbytte** – brukermenyen i admin bytter mellom Oslo Sportsklubb (fleridrett) og Bærum og Omegn Cykleklubb (én idrett, fem grener). Menyen, forsiden, fargene og «Om klubben» endrer seg med klubben. BOC har egne farger (gul flate, blå tekst), Grasrotandelen-panel, innmelding i Spond og nyhetsarkiv hentet fra klubbens egen side.
1. **Forsiden** `/` – «Finn gruppen din» i hero (alder, gren, nivå), «Klubbåret» for BOC med ritt, Mallorca-turer og Zwift-vinter, «Finn din aktivitet» (Grupper-menyen lagt ut på siden, med bilde av hver gruppe — `group-browser.tsx`, samme data som menyen via `src/lib/nav.ts`; samme modul på `/bli-med`), historier og logostripe. Enkeltøkter og påmelding ligger i Spond, så forsiden har ingen ukeoversikt.
2. **Laget** `/fotball/jenter/j16/j16-2` – en side generert fra hierarkiet, med «Sesongen 2026»: ukerytme, pauser, cuper og hvilket årskull som overtar ved nyttår.
3. **Barn og ungdom** `/barn-og-ungdom` – egen landingsside for foreldre: gruppene for barn gruppert per gren, med alder og treningstider. Voksengrupper som også tar imot ungdom står for seg selv.
4. **Aktiviteter** `/aktiviteter?gruppe=j16-2` – to faner: «Kommende» (Klubbåret fra forsiden øverst, «Året i ett blikk», styrt av sidens filter i stedet for egne knapper, og terminlisten under, åpen som standard) og «Treningstider» (ukerytmen); `#treningstider` og `#terminliste` i lenken velger fane. Ett filter for begge som velger: «Alle» eller én gren (idrett i et fleridrettslag), så avdeling › årsklasse › lag under den, der lenkene fra gruppesidene lander, og aldersvalget (Alle aldre / Barn og ungdom / Voksne). I treningstidene er like økter i flere grupper én rad («BOC 1–4»), en tittel som bare gjentar gruppenavnet vises ikke, og en økt som ikke har startet eller slutter snart er merket («fra 1 okt», «til 30 sep»). Hver dato i terminlisten har en etikett for typen med eget ikon og egen flate (`KindTag` i `activity.tsx`): ritt og kamp sterkest, turer og samlinger i klubbens gule, dugnad varm, arrangementer nøytrale. Grenfargene brukes ikke til dette, siden de allerede betyr disiplin i Klubbåret. Enkeltøkter og påmelding ligger i Spond; se `src/lib/timetable.ts` for hvorfor skillet går der.
5. **Publisering** `/admin/publiser` – bytt til Marte Solberg (lagleder J16-2) i brukermenyen, gjerne i mobilbredde.
6. **Personvern** `/admin/personer/p-nora` → *Anonymiser permanent*, og åpne så `/nyheter/j16-2-snudde-kampen-mot-lyn` på nytt.

Demo data can be reset from the user menu in admin (or by restarting the server). The reset and the club switcher exist outside production only; on the deployed site they are gone, and a request for them is refused.

## Architecture notes

- **Data**: typed mock store in memory (`src/lib/data/store.ts`), one per club, seeded from `src/lib/data/seed/`. Dates are relative to today, so «denne uken» always has content.
- **Schedule**: the site publishes the weekly rhythm (`TrainingSeries`) and the terminliste (dated matches, races, camps and open events). Single sessions, sign-ups and last-minute changes stay in the club's own planning tool — `src/lib/timetable.ts` holds the rule.
- **Times the club cannot promise**: not every session has a clock. A series that cannot promise one sets `startApprox`, keeps the earliest likely time as its sort key and says the rest in `note`; views with room print «ca.» before the range. The site never invents a start it cannot stand behind — `src/lib/timetable.ts`. BOC 1–4 no longer need it: they meet Tuesday and Thursday at 18.00 at Bekkestua torg and Sunday at 10.00 at Kaffebrenneriet, every week April–September except July, so each session is two series (April–June, August–September) and July stays empty everywhere.
- **Writes**: only through server actions in `src/app/actions.ts`, each checking permissions from `src/lib/permissions.ts`.
- **Permanent storage**: with `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` set (see `.env.example`), admin changes are stored in Supabase and survive restarts and deploys; without them they live in memory, as in local development. The seed in the code stays the base: only what was edited, added or removed in admin is stored (`src/lib/data/overrides.ts`), and it wins over the code. Groups, venues and weekly sessions are stored field by field (only the top-level fields that differ from the seed), everything else per record, so content changed in the code still reaches the site wherever nobody has edited that field; people and articles stay whole, since removing fields is how a person is anonymised. One row per club in the table `club_overrides`, written over Supabase's REST API with plain fetch (`src/lib/data/supabase.ts`, which also has the SQL to create it); every write checks the stored version, so two admins saving at once cannot overwrite each other. «Tilbakestill til utgangspunktet» in the admin menu deletes the row.
- **Sign-in by e-mailed code** (`src/lib/supabase-auth.ts`, `src/lib/session.ts`, `CodeLogin`): a person invited as a `User` (an e-mail, a role, not `active: false`) asks for a six-digit code on `/logg-inn`, the site makes the code with Supabase's admin `generate_link` (nothing sent by Supabase) and e-mails it itself through Resend from the sender that fits the host the person is on (`lib/code-mail.ts`, `mailSenderForHost` in `lib/mail.ts`: baerumock.no → `login@baerumock.no`, jakobjolstad.com hosts → `login@jakobjolstad.com`, anything else `MAIL_FROM`; override or add with `MAIL_FROM_HOSTS`=`host=Avsender <adresse>;…`; the sender domain must be verified at Resend). If that fails for any reason (no key, domain not verified), Supabase mails its own code instead (SMTP through Resend; the «Magic Link» template must print `{{ .Token }}`), and `verifyCode` accepts both kinds of code, and the code is swapped for an access and a refresh token kept in httpOnly cookies (`klubb-at`, `klubb-rt`, 14 days, renewed). Supabase's own sign-ups are off; the server creates the auth user only for an e-mail that is already an active User, and answers the same whether or not the address is known. Each request asks Supabase who the access token belongs to, so signing out (which also revokes the session at Supabase) or deactivating a user takes effect at once; `src/proxy.ts` renews an expired access token. The code field is a one-time-code field (iPhone offers the code from Apple Mail) and signs in at the sixth digit. Needs `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and the anon or publishable key (`SUPABASE_ANON_KEY` or `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`). BOC's seed has one active user, the club administrator; the others cannot sign in by code until invited. The shared password below stays as a second way in until the codes are in use.
- **Brukere** (`/admin/brukere`, club administrators only; `src/lib/user-admin.ts`, `UserManager`): everyone who can sign in, with their roles. A club administrator invites (name, e-mail, a first role; the site e-mails the invitation itself, from the Resend domain, with a button to `/logg-inn?epost=…` where the address is already filled in and the person then asks for a code; `lib/mail.ts`, `lib/invite-mail.ts`; without `RESEND_API_KEY`, or if Resend refuses, the user is still made and the page hands over a message to pass on; «Send invitasjon på nytt» in Administrer sends it again), adds and removes roles, edits name and e-mail, and deactivates or reactivates (`active: false` is turned away at the next request, history stays). Rules in `user-admin.ts`, enforced in the actions `inviteUser`, `updateUser`, `setUserActive`, `addUserRole`, `removeUserRole`: the club always keeps an active club administrator, nobody deactivates themselves, drops their own club-administrator role or changes their own address, a user keeps at least one role (to remove all access, deactivate), a club role sits on the club and every other role on one part of it, and an e-mail address belongs to one user. Each change is logged (`inviteUser`, `editUser`) with the user's id but no name or address in the text. The page warns about groups nobody active can publish for.
- **Admin menu, colours and profile picture**: the top bar has Oversikt, Innlegg and Sitater as plain links and folds the rest into two drop-downs, Klubben (Grupper, Struktur, Arenaer, Innstillinger) and Folk (Personer, Brukere), so it stays narrow however many pages there are; a group someone sees one page of is just that page (`NavGroup` in `admin-chrome.tsx`; groups and the short phone label `tabLabel` are set per item in `app/admin/layout.tsx`; on a phone the tab bar has Oversikt, the person's main page, the plus, Innlegg and «Mer», a sheet with every other page, so nothing in the top bar is out of reach). Each part of admin has its own colour from the design system's `--cat-*` pairs, the club's colours for the venues, and plain ink for the system pages (`components/admin/sections.ts`): a dot and the underline in the top bar, the tinted icon in the page header (`SectionBadge`), the active tab on the phone, the selected filter chip (`chipClass` reads `--accent`, set on `<main>`), and roles as coloured labels (`RoleChip`, `ROLE_HUE`). Buttons in admin have a 3 px radius (`--radius-button` in `.theme-admin`). Rows of filter chips in admin are grids with every choice visible instead of scrolling rows, and `.scroll-x` no longer scrolls up and down (`overflow-y: hidden`). The list of news articles (`/admin/innhold`, the address is kept) shows a thumbnail of each article's first usable picture through `Photo`, so redactions apply and a withdrawn photo is left out. «Bytt profilbilde» in the user menu opens `AvatarEditor`: choose a photo, drag and zoom it inside a round frame (pinch on a phone, the arrow keys and +/- on a keyboard), and the square that is shown is drawn on a canvas and uploaded as a 512 px JPEG, which also drops the file's metadata. `setOwnAvatar` and `removeOwnAvatar` only ever change the acting user (`User.avatar`), upload to Supabase Storage and delete the previous file there (`removeUpload`); the picture is shown in admin only (menu, Brukere), never on the public site, and is kept apart from the person register's portrait, which stays the fallback (`userPhoto` in `lib/user-admin.ts`).
- **Groups without a contact person**: the overview's warning («Grupper uten kontaktperson») links to `/admin/struktur?mangler=kontaktperson`. Struktur marks every group nobody is listed as trainer or team manager for (`StructureNode.missingContact`, the same rule as the warning: a leaf group with no `contactsFor(…, { inherit: false })`) in red, in the list and in the detail panel, and when arriving from the warning it opens the first of them and shows a red banner with a button per group to jump between them.
- **Folk: Medlemmer, Administratorer, Eksterne**: the Folk drop-down has three categories, Medlemmer (`/admin/personer`, the person register), Administratorer (`/admin/brukere`, who can sign in) and Eksterne (`/admin/eksterne`, `lib/externals.ts`, `ExternalManager`): people outside the register whom the club names, today the photographers of its pictures (a parent, a hobby photographer), with a name and a note for the club's own use. `Db.externals` is stored per record like people. Anyone with a role can add one (`addExternal`, so an upload is never held up; the same name, however written, is reused); only a club administrator renames or deletes (`updateExternal` renames the credit on the pictures too, `deleteExternal` refuses while a picture credits the person).
- **Pictures: photographer, who is in them, alt text and check** (`lib/photo-meta.ts`): every upload (the composer, a group's main photo, a venue's) must say who took the picture, `PhotographerPicker` (the uploader, the group's adult members, the externals, or the club's short name when the photographer wants no credit; an unknown photographer is added on the spot as an external; a child is never named), and who is in it, `PeopleTagger` (tick members of the group, «Velg alle» for all, or «Ingen identifiserbare personer på bildet»; blank is not an answer, and the upload cannot be sent until one is given; a venue is a place and counts as no people). The credit shown as «Foto: …» follows the photographer (`Photo.photographer`, `Photo.credit`), the alt text is written by the system and names nobody («Bilde 2 av 5 fra Ungdom, 5. oktober 2026. 3 medlemmer er med.», `autoAlt`; `altWithPeople` brings the member count up to date when an administrator corrects the tagging), and anonymising a member who is credited changes the credit to the club's. A picture goes live at once; `Photo.review` starts as `pending` and a club administrator checks it afterwards on `/admin/bilder` («Godkjenn», or «Rett» to correct photographer and tagging first). A club administrator's own uploads are approved at once. A picture that has waited `PHOTO_REVIEW_DAYS` (3) days turns the warnings red: a red count on «Bilder» in the menu, a red line on the overview, a red banner and red rows on the page. Pictures from the composer are stored in Supabase Storage (only their address is kept in the club's data), checked for type and size (`storeComposerPhoto`).
- **Admin lock**: in production the only way in is the e-mailed code (`CodeLogin`, `src/lib/supabase-auth.ts`, `src/lib/session.ts`); the shared password and the demo user picker are gone there, and a leftover `ADMIN_PASSWORD` is ignored (`src/lib/admin-auth.ts`). Pages need a session cookie (`src/proxy.ts`, Next 16's name for middleware), and every server action asks who is signed in (`context()` in `actions.ts`); without a valid user `loadAdmin` sends you to `/logg-inn` and actions refuse. Locally, without the e-mail sign-in set up, `/logg-inn` offers a mock sign-in and the demo users (`LoginFlow`), and with `ADMIN_PASSWORD` set the dev server asks for it. The page fills in the address from an invitation link, or else from the last address that signed in on the device (localStorage).
- **Hierarchy**: `src/lib/org.ts`. Levels below sport are optional; page templates are chosen by position in the tree. A level with a single group under it is skipped (`org.soleGroup`): its links go straight to the group, its own address forwards there, and the group's breadcrumb leaves it out — BOC's Banesykling holds only Banegruppa.
- **Barn og ungdom** (`/barn-og-ungdom`): the club from a parent's side, with its own title and description. A parent searching «sykkelklubb barn bærum» is navigating, not deciding, while the front page has to give an undecided adult a reason — one hero cannot do both without saying nothing. The search query never reaches the site, so the routing is done by giving the engine a better page to send them to, not by switching anything at runtime. `youthExplorer` in `src/lib/finder.ts` splits groups *for* children (their age range ends inside youth) from adult groups that also take someone young (open-ended, but entered at 16 or under) — «fra 17 år» really means 17 to 99, so folding those in would list the whole adult club as a children's offer. Clubs with no children's groups get no page and no link to one — `hasYouth` in `src/app/(public)/layout.tsx` decides, and the header, the phone sheet and the footer all follow it.
- **Member quotes**: «Fra medlemmene» under the partners on the front page (`QuoteStage`, below). Each quote in `Club.testimonials` points at a Person, so first name, age (from birth year), groups and portrait come from the register and follow its privacy rules — a restricted or anonymised person's quote disappears, and a portrait shows only with photo consent. The cards follow Stripe's customer stories: a tall photograph with name, age and group set on it, the quote under it, and «Les … historie» to the member's story — an Article with `memberStory`, kept out of the news lists; an `example` article says so in a notice at the top. Paged like GroupCarousel. BOC's seven — BOC 1, BOC 3, Junior, BMX, Zwift, Downhill and BOC 4 — are placeholders on invented demo riders, with illustrated portraits in club kit supplied by the site owner (one stock photo from Unsplash), tagged «Eksempel» on the page; a quote is presented as a member's own only once that member has given it.
- **Sykle med …**: a member story (`Article.aboutPersonId`) ends with where and when to ride with that member — each of their groups with its weekly times merged per meeting point («Tirsdager og torsdager kl. 18.00 på Bekkestua torg», `Venue.preposition`) and its season over the whole year («april–september, unntatt juli»), from `rideWith` in `lib/views.ts` — and «Følg … på Strava» from `Person.stravaUrl`. The demo riders use the site owner's profile as a placeholder. «Bli med i BOC på Strava» (`Club.stravaClubUrl`, club 1026) sits on Om klubben and Bli medlem. Every Strava link is a button in Strava's orange (#FC5200) with white text set like every other large button (3.3:1, below AA for text that size) — «Bli med i BOC på Strava», «Følg … på Strava» — within Strava's brand guidelines: a plain-text reference, no logo (`strava-link.tsx`).
- **Glossary**: club words in running text («disipliner», «regler for gruppekjøring») get a dotted underline, an «i» and a tooltip with a short explanation and a link (`GlossaryText` in `glossary.tsx`, entries from `lib/glossary.ts`). The explanations are built from the club's data: its disciplines from the structure, the rules from `OrgNode.ridingRules`. Used in page descriptions, the Om klubben list, the join steps and the membership note.
- **Når og hvor on a branch**: a branch whose groups keep one simple rhythm (`simpleSchedule`, BOC 1–4 on Landevei) shows their «Når og hvor» as well, headed «For BOC 1–4.» (`groupNamesLabel` in `lib/group-names.ts`): the shared meeting points, times and months from `meetUpPlan` in `lib/meet-up.ts`, the same function the group pages use.
- **Riding rules**: BOC's rules for riding together are data on Landevei (`OrgNode.ridingRules`), inherited down the tree like `leadTitle`. `RidingRules` (`node/riding-rules.tsx`) shows the nearest ancestor's list as «Slik sykler vi sammen» on Landevei, its youth section and every group under them; nodes without rules above them show nothing.
- **Group presenter**: every group page opens with the person who presents it, in a card of their own under its description (`GroupLead`: a large portrait, name, role, phone or e-mail and a link to all contacts) — the team manager (lagleder) if it has one, then its head coach, a coach, or the section lead it inherits (`presenterFor` in `src/lib/content.ts`) — with a link to the contacts. The card names the role in the club's own word, `leadTitle`, inherited down the tree: BOC says «Gruppeleder», and «Road Captain» on Landevei. A person's `portraitPhotoId` is shown there and in the contact list only while they are visible and have consented to photos (`portraitOf`); until then their initials stand in. No demo person has a portrait: several BOC names are the club's real volunteers, and a stock face must not stand in for a real person.
- **Dark pages**: a group with `pageTone: "dark"` renders its whole page dark (`.page-dark` in globals.css) — Zwift, ridden in the evening and often in a dark room. Like `.header-dark` it redefines the semantic tokens for the subtree, so no component needs to know; the ground is the club's dark header colour and links take the header's link colour.
- **Announcements**: a group can carry an `announcement` — a band in the club colour straight under its hero, for something its riders must not miss (Banegruppa's next course, Zwift's Fryd Vinterligaen). With `opensAt` it switches from `title` to `titleOpen` on the moment a sign-up opens, and it goes after `until`. With `inline` it is a compact note in the weekly plan instead (Zwift's Fryd Vinterligaen). A group can also leave out sections that say nothing for it (`hideSections`): Zwift drops the terminliste and the season summary.
- **Når og hvor**: a group with one simple rhythm (`simpleSchedule`, BOC 1–4) gets one section, above its terminliste, in place of the season summary and the weekly plan (`meet-up.tsx`): a card per meeting point with its days and clock set large and a way to get there, and the twelve months as a strip — season months filled, a break inside the season hatched and named. Its terminliste also carries the rides the group trains towards (`Race.groupIds`): at the next edition, projected from the organiser's last one until it is announced, with «ca.» in place of a weekday. A node can also name groups whose season belongs in its terminliste and every page below it (`seasonsInTerminliste`, `terminlisteSeasons` in `club-year.ts`): Landevei carries the Zwift season, linked to the Zwift group, since that is where its riders go for the winter.
- **BOC's facts from the annual meeting**: membership rates (`Club.membership.rates`, 2026 with the 2027 rates in the note), the road groups' leaders, the rides each group enters, the training times and the committees follow the papers for the annual meeting of 11 March 2026 and årsberetningen 2025 in them. A committee member's title carries the role after a comma («Valgkomité, leder»), and /styret shows it as Leder, Medlem or Vara. The club's Trondheim–Oslo team (BOC T-O) rides at BOC 3's level and trains with it, so the site shows the two as one group, «BOC 3» everywhere and «BOC 3 / BOC T-O» as the heading on its own page (`OrgNode.pageHeading`), with the team's leaders among its Road Captains, rather than as two offers for the same riders.
- **Members**: an adult group names a member only when that person is visible, 18 or older, has said yes to photos and has a portrait (`portraitOf`), one tile each (`MemberGrid`, section «Gruppa»); everyone else, children included, is only a number: «12 utøvere i BOC 1», then «og 10 andre medlemmer» under the tiles. The section appears when at least one member can be shown. A coach heads the list only with a portrait too (coaches are listed as contacts on the page either way). In a group for adults (`ageRange` from 17) the group's own coaches, BOC's Road Captains, head the list with their title under the name: they ride with the group, and the role vouches for their age. A tile shows the portrait with photo consent, otherwise initials. BOC 1 and 2 carry invented adult riders for it. The group's fact row shows a squad size only for football; a group can name its `seasonFocus` instead (BOC 1: Vätternrunden).
- **Privacy**: `src/lib/privacy.ts`. People are linked to content structurally (photo regions, text mentions with neutral wording, activity slots). Anonymisation rewrites the stored content permanently.
- **Design system**: tokens in `src/app/globals.css`, club colours as CSS variables per club. A club has two brand colours: `primary` paints surfaces and buttons (BOC's yellow), `link` is the same brand as text and must stay readable on white. Reference at `/design-system`.
- **Hero**: one band — the photograph, with the statement on it. That only works because two things left it: the finder, which now has a section of its own, and a headline that used to run to five lines. Together they forced a treatment that swallowed the picture, and the picture is what says what kind of club this is. The statement now ends at 56 % of the width while BOC's riders in club kit sit from 62 % out, so `.hero-scrim` (globals.css) treats the bottom-left corner and leaves them alone: a bottom-up tone and a second one fading out sideways. Colour only — blur was tried and dropped, because it costs photograph everywhere it reaches, so contrast against a light picture now rests on the gradients alone. A hero photo for this design needs its subject in the right half or high in the frame. Nothing is asked of anyone above the fold. Set `heroVideoUrl` on the club (a file in `public/`, or any URL) and the band plays film instead, with the hero photo as poster and fallback.
- **What the statement says** (`identity.headline` / `intro` per club): two jobs in one breath. The weekly training leads, because it is what a member actually gets — 28 of BOC's sessions a week are fellestrening, and «hele året» is the road through the summer and spinning and Zwift through the winter. The races and Mallorca follow, because an adult comparing the club to the free social rides nearby is not asking which group fits their age (the rides have levels too) but why join a club at all, and those are the part a ride cannot arrange. The supporting line names both audiences, so a parent knows in one sentence that they are in the right place. One low-commitment action follows it, «Se klubbåret» rather than «Bli medlem», with a second door to `/barn-og-ungdom`. Clubs without `identity.year` fall back to «Finn din aktivitet».
- **Front-page grounds**: the sections under the hero alternate white and light grey, counted over the sections a club actually shows (the club year, the editorial story and the kit are optional), so no two neighbours share a ground.
- **Klubbåret is written as an argument**, not a description: it has to say what a membership buys that turning up to a free group ride does not.
- **Group finder**: the card asks age, one or more branches (or sports) and level, with back and forward arrows; it skips any question whose answer would not change the result, and ranks groups by level distance, the club's pick (`recommendFirst`, set on Zwift) and age span (`src/components/public/group-finder.tsx`). Recommendations are dealt one per chosen branch before any second group, since a member can ride with a group in each. The best match is set as an answer to «what do I do now?» (`LeadResult`): the group, what it is like in its own words, its pace and days where the summary does not already say them, the club's words on trying before joining, and a link to the group page's «Før første trening» — not to membership. The rest follow as rows. The card has a minimum height and grows for the result rather than clipping it. It sits in its own section under the statement and the club's numbers, not in the hero: asking «how old are you?» before the page has given a reason gets an answer from nobody, and ODP puts its own levels below the fold for the same reason. Age is picked from bands (`AGE_BANDS`), not typed: a number field answers one person's question and hides the club's shape, while the ladder shows at a glance that the road groups take everyone from 17 upwards — 19–39, 40–59 and 60+ all return the same eleven groups. A band matches a group when the two ranges overlap, and every result row carries the group's own age label, so a partial overlap reads honestly. Bands with nothing in them are shown disabled, because «no group for a seven-year-old» is an answer too. The bands stand in two columns, «Fra 17 år» first and «Barn og ungdom» (up to 16) beside it, the same split as the membership fees and the adult road groups, so a parent finds the child's column without reading the adult ladder. Groups declare the levels they welcome in `levels`; the scale in `src/lib/levels.ts` has three steps, all below racing, described by what someone has done rather than what they are (people place themselves badly on «nybegynner … aktiv mosjonist», but know whether they have ridden in a group). A discipline words the steps in its own terms (`OrgNode.levelOptions`: Landevei asks about riding in a group, Terreng about technical trail), used when it is the only one chosen; a child's age band asks about the child. The choices are radio groups with arrow keys and one tab stop, as native radios. Someone who already races knows which group is theirs; everyone else is placing themselves against people they have never met, and a fourth, faster step made the whole ladder read as a club for fast riders. The road groups list one or two adjacent steps, which is what lets the finder put BOC 4 first for a beginner and BOC 2 first for an active rider. Branch icons are drawn to Feather's grid in `branch-icons.tsx`. The one-line schedule on a group card (`scheduleSummary` in `src/lib/finder.ts`) only names a time or a place when every session of the group shares it.
- **Hero band**: edge to edge up to 1728 px — the width a 16" MacBook Pro reports — and always square and flush under the header. Above that the photograph keeps its 1728 px and the band carries on to the screen edges in the header's colour (`--header-bg`, black for BOC; the inverse surface for a club with a paper header), so the picture never stretches across an ultrawide display. It fills the viewport below the header (`100svh`), clamped between 38rem and 52rem, and settles at a fixed 38rem once the photograph stops at 1728 px. Below lg (1023 px and down) the band comes apart: the photograph alone, 4:3 across the screen width, then the statement and its actions on the header's colour, then the numbers two by two — so nothing sits on the picture and it needs no scrim. It does not guess: a person already linked to another user does not count, an address that stands on several people (a parent's on each child) belongs to the adult among them only if there is exactly one, and otherwise the user gets a new person as before. A user who already has a person of their own (one made at the invitation) is left alone; two records for one human is for an administrator to merge. The Spond import still reads no e-mail, so addresses come from the person's page (`/admin/personer/<id>/rediger`) until the import is extended.
- **Merging duplicates in the register** (`mergePeople`, `mergeProblem` in `lib/merge-people.ts`, `mergePeopleAction`, «Slå sammen» in the member list's bar, club administrators only, two to ten people): tick the duplicates and choose which record to keep (suggested: the one with an account, then a birth year, then the most groups). Groups, e-mail, birth year or date, phone, portrait and guardian links are gathered on it (its own values win), the stricter privacy answer wins (a «Ikke publiser» or a «nei» is never turned into a yes), and everything that pointed at the others points at it: photo tags, mentions in published text, quotes (a duplicate quote is dropped), dates, consent and privacy requests, who took a picture, the log, and users' `personId` and guardian links; then the others are removed. It is refused when the names differ, the birth years or dates differ (a father and a son with one name), or more than one has an account of their own (merge the accounts first, `linkUserToMember`); the dialog says why before anything is sent, and the server checks again. It cannot be undone.
